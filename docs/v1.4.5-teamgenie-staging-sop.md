# Dujiao-Next v1.4.5 TeamGenie Staging SOP

Date: 2026-08-27

## Scope

This SOP upgrades the custom TeamGenie build to the official `v1.4.5` architecture while keeping the existing `unicard-themes` storefront as the public root UI.

Do not run the official production upgrade blindly. This project has custom backend sync logic, custom contact channels, and a custom storefront.

## Source Baseline

- Official base: `v1.4.5`
- Custom branch: `teamgenie-v1.4.5`
- Custom commit: `a1fdd7d4 feat(teamgenie): port fulfilled sync to v1.4 architecture`

## Current Recommended Topology

First production phase:

- Keep `unicard-themes` at public root.
- Replace old `dujiaonext-api` + `dujiaonext-admin` with new fullstack backend `dujiaonext`.
- Proxy `/api/`, `/uploads/`, `/health`, and `web.admin_path` to the new backend.
- Keep `teamgenie-sync`, PostgreSQL, and Redis.

Reason:

- It preserves the current customer-facing storefront.
- It allows the official embedded admin to move to the new `web.admin_path`.
- It avoids porting the React storefront into upstream `frontend/user` during the first upgrade.

## Config Changes

Production `config.yml` must include:

```yaml
app:
  secret_key: "persistent-strong-random-secret-keep-forever"
  totp_issuer: "MoshShop"

web:
  admin_path: "/replace-with-private-admin-path"

teamgenie_sync:
  enabled: true
  webhook_url: "http://teamgenie-sync:8788/path-from-current-config"
  shared_secret: "keep-current-secret"
  channel: "keep-current-channel"
  source_platform: "keep-current-source-platform"
  source_site: "keep-current-source-site"
  timeout_ms: 3000
```

Keep current database, Redis, upload, email, captcha, payment, and order config values.

Important:

- `app.secret_key` is required by `v1.4.5`; generate it once and keep it unchanged permanently.
- `web.admin_path` must be the same path used in Nginx.
- Do not use `/admin` in production unless intentionally accepting the scan risk.
- Do not print or paste secrets into shell history beyond the VPS config file workflow already used.

Generate a candidate secret on the VPS:

```bash
openssl rand -hex 32
```

Do not regenerate `app.secret_key` after production cutover.

Run the production readiness audit before cutover:

Then run the printed command on the VPS:

```bash
sudo bash /tmp/dujiao-next-v1.4.5-production-readiness.sh
```

If the audit reports missing `app.secret_key` or `web.admin_path`, upload and run the config patch helper:

The helper backs up `config.yml`, adds a persistent `app.secret_key` if missing, and adds `web.admin_path`. It does not restart containers.

## Staging Rehearsal

Preferred rehearsal uses a copied database, not the production database, because `v1.4.5` can run schema migrations.

Helper-based rehearsal:

```bash
cd /Users/cike/dujiao-next/dujiao-next-v1.4.1-teamgenie
bash scripts/prepare-v1.4.5-staging-helper.sh dujiao-vps
```

Then run the printed command on the VPS, replacing the backup directory with the fresh backup path:

```bash
sudo bash /tmp/dujiao-next-v1.4.5-staging-restore.sh /opt/backups/dujiao-next-v1.4.5-preflight-YYYYmmddHHMMSS
```

The helper creates isolated staging containers:

- `dujiaonext-postgres-staging`
- `dujiaonext-redis-staging`
- `dujiaonext-staging`

The staging backend listens only on `127.0.0.1:18081`, uses `web.admin_path` `/staging-admin-v145`, and forces `teamgenie_sync.enabled` to `false`.

Minimum staging approach:

1. Restore the backup dump into a separate PostgreSQL database or separate Docker volume.
2. Copy production `config.yml` and adjust DB DSN, ports, and `web.admin_path`.
3. Start the new `dujiaonext` service on a non-public port.
4. Point a temporary Nginx server name or local SSH tunnel at the staging ports.
5. Run the regression checklist below.

Avoid starting the new `v1.4.5` binary against the real production DB until backup and rollback are ready.

## Production Cutover Outline

After staging passes:

1. Confirm fresh backup exists.
2. Build image `dujiaonext/dujiao-next:teamgenie-v1.4.5` on VPS.
3. Confirm production config contains persistent `app.secret_key` and private `web.admin_path`.
4. Upload the guarded cutover helper:

```bash
cd /Users/cike/dujiao-next/dujiao-next-v1.4.1-teamgenie
bash scripts/prepare-v1.4.5-production-cutover.sh dujiao-vps
```

5. Run dry-run on the VPS first:

```bash
sudo bash /tmp/dujiao-next-v1.4.5-production-cutover.sh
```

6. Review generated candidate compose and Nginx files under the printed cutover directory.
7. Apply only after dry-run output is clean:

```bash
sudo bash /tmp/dujiao-next-v1.4.5-production-cutover.sh --apply
```

The helper backs up current compose and Nginx files, swaps port `8081` from the old API container to the new fullstack `dujiaonext` container, adds `web.admin_path` and `/health` Nginx routes to the new backend, validates health, reloads Nginx, and rolls back if the new backend fails its local health check.

## Rollback

If `v1.4.5` has touched production DB migrations, rollback requires restoring the database dump.

Keep until stable:

- Old compose file with `dujiaonext-api` and `dujiaonext-admin`
- Old Nginx config
- Old images:
  - `dujiaonext/api:teamgenie-sync`
  - `dujiaonext/admin:v1.3.1`
  - `nginx:alpine` storefront runtime
- Backup directory under `/opt/backups/`

Fast rollback shape:

1. Stop new `dujiaonext` service.
2. Restore old compose/Nginx.
3. Restore DB dump if migrations ran.
4. Start old `dujiaonext-api`, `dujiaonext-admin`, and `unicard-themes`.
5. Verify `/health`, public config, admin, storefront, and TeamGenie health.
